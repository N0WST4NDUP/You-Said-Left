# 이슈 단위 작업과 TDD

한 가지 목적의 작업을 독립적으로 검증하고, 완료한 변경을 커밋으로 기록하기 위한 흐름이다. AI는 범위·테스트 설계, 실행 확인과 리뷰를 돕고, 게임 코드는 사용자가 직접 작성한다. 코드 변경 권한과 커밋·푸시 범위는 [AGENTS.md](../AGENTS.md)를 따른다.

## 작업 단위와 완료 조건

이슈는 완료할 작업의 범위를, 테스트는 기대하는 동작을, 커밋은 검증한 변경을 기록한다. 하나의 이슈 안에서 여러 TDD 반복과 여러 커밋이 생길 수 있다. 이슈 하나를 테스트 하나 또는 커밋 하나와 반드시 맞추지 않는다. 각 커밋은 한 가지 목적을 가진 변경으로 묶는다.

작업을 시작하기 전에 최신 Git 상태, 관련 이슈, 현재 소스와 작업 문서를 확인하고 다음을 정한다.

- **목적·범위**: 이번에 추가하거나 고칠 한 가지 기능 또는 동작 계약.
- **제외 범위**: 다음 작업으로 남길 기능과 이번 검증으로 보장하지 않는 것.
- **선행조건**: 필요한 결정, 기존 API와 관련·상위 이슈. 미정 계약은 구현 전에 정한다.
- **검증 조건**: 입력·상황에 따른 기대 결과, 검증 방법과 필요한 증거.

검증 조건은 구현 방식보다 관찰 가능한 결과로 적는다. 예를 들어 “연결 코드를 작성한다” 대신 “없는 노드 ID로 연결을 요청하면 예외가 발생하고, 기존 양방향 연결은 유지되며 잘못된 직접 연결은 양쪽 모두 저장되지 않는다”처럼 적는다. 관련 정상 동작, 경계 입력과 실패 후 상태 보존을 함께 고려한다.

하위 작업만으로 완료 조건을 충족할 수 있고, 다음 기능을 구현하지 않아도 그 결과를 검증할 수 있어야 독립적인 이슈로 본다. 범위가 여러 목적을 포함하면 상위 이슈 아래에 작은 작업을 나눈다. 예를 들어 청사진 생성이라는 상위 목표 아래에서 포트 소속 표현과 포트 판정 결과의 그래프 연결 적용을 각각 다룰 수 있다. 두 번째 작업의 선행조건은 첫 번째 계약이다.

현재 작업으로 합의한 독립 범위와 검증 조건은 작은 작업 이슈 또는 상위 이슈의 체크리스트에 명시한다. 그 범위가 완료되면 상위 이슈가 열려 있어도 커밋을 추천한다. 새 하위 이슈 등록 자체를 커밋 추천의 선행조건으로 삼지 않는다.

조건을 정한 것과 실제로 충족한 것은 구분한다. 테스트를 통과시키기 위해 기대 결과를 구현에 맞춰 바꾸거나, 필요한 검증을 사후에 제외하지 않는다. 요구사항 변경이 필요하면 근거와 바뀐 범위를 먼저 명시한다.

## 작은 TDD 반복

1. 이슈의 검증 사례 목록을 정한다. 목록은 작업 중 발견한 사례로 보완할 수 있다.
2. 다음 **한 가지 동작**을 실행 가능한 테스트로 작성한다. 모든 테스트 코드를 한꺼번에 작성하지 않는다.
3. **RED**: 실행해서 미구현 동작 때문에 예상한 결과와 다르게 실패하는지 확인한다. 환경 오류나 테스트 준비 실수는 의도한 RED로 기록하지 않는다.
4. **GREEN**: 사용자가 최소 구현을 작성하고, 새 테스트와 기존 관련 테스트를 실행해 통과를 확인한다.
5. **리팩터링·리뷰**: 필요한 구조 정리와 테스트의 허점·경계 사례를 검토하고, 변경했다면 다시 실행해 GREEN을 유지한다. 다음 동작을 미리 추가하지 않는다.
6. 현재 합의한 독립 범위에 남은 검증 사례가 있으면 2번으로 돌아간다. 해당 범위의 완료 조건을 충족하면 아래 커밋 추천 단계로 넘어간다.

이미 구현된 동작에 테스트를 추가하면 바로 GREEN일 수 있다. 이는 회귀 검증이며, RED를 만들기 위해 기존 코드를 일부러 깨뜨리거나 새 기능의 TDD였다고 기록하지 않는다. 버그 수정에서는 원래 오류를 재현하는 테스트의 실패를 확인한 뒤 최소 수정과 재검증을 진행한다.

TDD의 핵심은 RED → GREEN → 필요한 리팩터링의 반복이다. 이슈 생성·커밋·종료는 이 반복을 관리하고 기록하는 절차다. 테스트가 한 번 통과했다는 사실만으로 이슈 전체를 완료했다고 판단하지 않는다.

## 검증 방법과 증거

모든 완료 조건을 단위 테스트로 바꿀 필요는 없다. 검증하려는 내용에 맞는 방법을 선택한다.

| 확인할 내용 | 검증 방법과 기록 |
|---|---|
| 데이터·알고리즘·예외·상태 보존 | 자동 테스트의 고정 입력과 기대 결과, 실행 명령·결과 |
| Unity 컴파일과 Editor 테스트 | 현재 소스로 실제 Editor에서 확인한 컴파일·테스트 결과 |
| 게임 동작·화면·모듈 조립·주행 | Play Mode와 Game View의 고정 재현 절차, 기대 결과와 관찰 결과 |
| 의존성·저장소 규칙 | 소스·참조 확인과 해당 검사 결과. [저장소 검사 도구](tools/repository-checks.md)의 보장 범위를 구분 |
| 문서·설정 변경 | 변경 내용과 관련 참조의 일치, 링크 대상과 형식·diff 검사 등 변경에 필요한 확인 |

완료 시점에는 변경 후 현재 소스로 필요한 검증을 실행한다. 자동 테스트 변경은 해당 사례뿐 아니라 기존 동작을 보호하는 프로젝트 테스트도 확인한다. 실행 시점·대상·명령, 통과·실패·스킵과 미실행 항목을 기록한다. 기존 실패라고 설명할 때도 근거를 확인하고 숨기지 않는다. 과거 문서의 통과 기록을 현재 통과 결과로 재사용하지 않는다.

저장소 검사 통과는 Unity 컴파일·플레이 검증을 대신하지 않는다. 그래프 연결 테스트 통과도 실제 도로의 조립·주행 가능성을 보장하지 않는다. 논리 계약만 다루는 이슈는 그 범위를 명시하고, 화면·주행은 별도 작업으로 남긴다.

## 완료하면 커밋을 추천한다

다음 조건을 충족하면 해당 작업의 완료 경계로 판단한다.

- 현재 합의한 독립 범위와 그 범위의 모든 완료 조건을 충족했고, 필요한 현재 검증 결과가 있다. 상위 이슈 전체의 완료를 기다리지 않는다.
- 필수 검증의 미실행·실패와 범위 안의 미해결 문제가 없다.
- 필요한 리뷰·리팩터링을 마쳤고, 관련 API·작업 현황 문서가 변경과 일치한다.
- 기존 사용자 변경을 보존하면서 이번 목적에 해당하는 커밋 파일을 구분할 수 있다.

이 경계에서는 **다음 기능·이슈로 자동 확장하지 않고 먼저 커밋을 추천한다.** 추가 기능이나 관련 없는 정리를 끼워 넣지 않는다. 다음 작업은 사용자가 진행을 지시하면 시작한다. 사용자가 커밋 없이 다음 작업을 진행하라고 명시하면 그 지시를 따른다.

커밋 추천에는 다음을 짧게 제시한다.

1. **완료 범위**: 관련 이슈와 현재 독립 범위의 어떤 완료 조건을 충족했는지. 상위 목표가 남았으면 함께 명시한다.
2. **검증 근거**: 실제 실행 결과와 이번 범위에서 보장하지 않는 것. 미실행 필수 검증이 있으면 완료 추천 대신 남은 검증을 알린다.
3. **포함 파일**: 한 가지 목적의 구현·테스트·관련 문서. 사용자 변경이나 다음 작업 파일은 구분한다.
4. **메시지 제안**: 저장소 [메시지 형식](../.gitmessage)을 따르는 제목과 필요한 검증 기록·이슈 참조.

추천 문장은 “이번 독립 범위의 완료 조건을 충족했으므로 이 변경을 먼저 커밋하는 것을 추천합니다”처럼 작성한다. 실제 커밋은 사용자가 요청한 범위에서만 실행한다. 이미 해당 범위의 커밋을 요청했다면 재승인을 요구하지 않고 그 지시를 따른다. 커밋·푸시·GitHub 이슈 종료는 각각 요청받은 범위를 확인한다.

진행 중이거나 상위 목표가 남아 있으면 `Refs: #번호`로 연결한다. 이슈 전체의 완료 조건을 충족한 변경에는 `Closes #번호`를 제안할 수 있다. 하위 작업 완료만으로 상위 이슈를 닫지 않는다. GitHub의 자동 종료는 해당 커밋이 기본 브랜치에 반영될 때 적용되므로 로컬 커밋과 이슈 종료를 같은 사건으로 보고하지 않는다.
