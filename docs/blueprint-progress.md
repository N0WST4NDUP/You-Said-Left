# 청사진 작업 현황과 다음 세션 안내

기준일: 2026-10-10. 기능 추가 또는 검증 결과가 바뀌면 이 문서를 함께 갱신한다. 현재 API는 [Blueprint API](api/blueprint.md)와 [RoadNetwork API](api/road-network.md), 지형 우선 방향은 [ADR-005](decisions/ADR-005-terrain-first-generation-with-tunnel-caves.md), 입체 도로 연결·공간과 후속 순서는 [ADR-006](decisions/ADR-006-separate-terrain-and-grade-separated-road-network.md)를 따른다. 도로 노드·직접 연결의 저장과 BFS 도달 여부 조회, 포트의 논리 경계 높이·방향·인접성 및 없는 노드 연결의 상태 보존을 검증했다. #7의 노드 ID별 포트 등록·조회와 상태 보존까지 전체 100개 Editor 테스트의 GREEN을 확인했다. 이번 독립 범위의 커밋 추천 이후 노드·타일·모듈과 좌표 관계를 별도로 정리한다. 포트 판정의 연결 적용, 비용 최적화·공간·조립 계약은 후속 범위다.

## 확정한 방향

- 청사진을 원본으로 3D 도시와 조수석의 종이 지도를 만든다. ([ADR-001](decisions/ADR-001-blueprint-as-source-of-truth.md))
- 격자와 Low Poly Epic City의 모듈을 사용한다. ([ADR-002](decisions/ADR-002-grid-generation-with-modular-tiles.md))
- 마인크래프트의 지형 생성 기법을 참고한 변화하는 지형에 GTA 산안드레스처럼 차량으로 주행할 수 있는 도로망을 구성한다. 첫 지형 검증부터 고저차와 물을 포함한다. 특정 Minecraft 버전의 전체 생성 알고리즘을 채택한 것은 아니다.
- 높이는 정수 층과 경사 모양으로 표현하고, 한 층을 6 Unity 단위로 조립하는 방향이다. 현재 디버그 표시의 높이 배율과 구분한다.
- 물은 공통 수면부터 구현한다. 물 셀의 `Level`은 바닥이고 `WaterLevel`은 수면이다.
- 지형 높이와 도로 높이를 분리하고 지상도로·경사·터널·교량·고가도로를 표현한다. 같은 수평 위치의 여러 도로가 겹쳐도 연결용 램프·접속점이 없으면 서로 이어지지 않는다.
- 동굴의 3D 표현은 터널 모듈을 사용한다. 차량용 터널은 입구·내부·출구 연결과 빈 공간을 함께 다룬다. 자연 동굴 선생성 여부는 아래 미해결 항목으로 구분한다.
- 생성 순서는 지형·물 → 자연 동굴 공간(채택 시) → 출발지·목적지와 입체 경로·공간 예약 → 건물 → 상세 도로·터널·교량·고가 구조 조립 → 장식·지도 → 검증이다. 도로 계획은 건물 전, 상세 조립은 건물 이후다.
- 자동 생성에 앞서 수동 청사진으로 저장·연결 계약부터 검증한다. 도달 가능성, 모듈·공간 유효성, Play Mode와 Game View의 차량 주행, 지도 일치는 각각 확인한다.

## 현재 구현

| 구성 | 소스에서 확인한 상태 |
|---|---|
| `Blueprint` | 크기·기준 높이·선택적 수면을 저장하는 class. `TerrainCell[,]`과 셀 조회·교체, 범위 안 상하좌우 이웃 좌표 조회 제공 |
| `TerrainCell` / `TerrainKind` | `readonly struct`인 셀에 절대 높이 층과 Grass/Water 종류 저장 |
| `BlueprintGenerator` | Grass 초기화 → 주입한 샘플러로 높이 적용 → 수면보다 낮은 셀만 Water로 분류 |
| `PerlinLevelSampler` | Perlin 샘플을 정수 높이 오프셋으로 변환. 시드는 샘플링 원점 선택에 사용 |
| `TerrainLevelQuantizer` | 유한한 노이즈와 정상적인 최대 오프셋 입력을 정수 높이 구간으로 변환 |
| `BlueprintSceneDebug` | Scene Gizmos로 초록 지형, 연하늘 수면과 회색 물속 바닥 테두리를 표시하는 코드 존재 |
| `RoadNode` / `RoadNetwork` | 읽기 전용 노드의 ID·수평 좌표·절대 도로 높이 저장, ID 조회, 중복 ID 거부, 명시적 양방향 직접 연결 저장·조회, BFS 도달 여부 조회. 노드 ID별 포트 등록·스냅샷 조회, 없는 소속 ID의 예외·상태 보존 |
| `RoadPortSide` / `RoadPort` / `RoadPortMatcher` | 네 수평 격자 방향과 읽기 전용 셀 주소·방향·경계 높이 저장. 같은 높이, X·Y축 반대 방향과 그 방향에 맞는 바로 이웃 셀 검사 |

현재 코드는 [Core/Blueprint](../Assets/Scripts/Core/Blueprint)와 [BlueprintSceneDebug.cs](../Assets/Scripts/Helper/BlueprintSceneDebug.cs)에 있다. 기존 지형 구현의 기준점은 `c6ca90d`, 도로 노드·연결·도달 조회와 입체교차·램프 검증의 기준점은 `0048f16`이다. 디버그 컴포넌트가 존재한다는 사실과 실제 화면 확인은 별개다.

### 아직 구현하지 않은 것

- 경사 모양·방향과 조립 가능한 높이 경계 제약.
- 출발지·목적지, 필수 경로 예약, 건물·도로·장식 배치.
- 중복·자기 연결 등 남은 입력 경계의 정책·검증, 노드·타일·모듈의 대응 및 좌표 관계 정리, 모듈 소속과 포트 판정 후 연결 적용, 경로 목록·비용 최적화, 도로 형상·타일 포트의 형식 및 실제 조립 위치·높이 검증.
- 터널의 지하 연결·빈 공간, 교량·고가도로·램프와 3D 점유·여유 공간의 데이터 및 조립.
- 실제 도시 조립기와 종이 지도 렌더러.
- 바다·호수 구분, 강·물 흐름.
- 특성 시스템. 생성기의 `ApplyTraits`는 비어 있으며 생성 과정에서 호출되지 않는다. [ADR-003](decisions/ADR-003-trait-selection-before-random-levels.md)은 `Proposed`다.

현재 셀의 이웃 조회는 좌표 인접성만 반환한다. 물·높이·경사·도로 연결을 검사하거나 통행을 보장하지 않는다. Water도 지형 분류일 뿐 모든 높이의 도로를 차단한다는 뜻은 아니다. 물 위 교량은 별도 도로·공간 조건으로 판단해야 한다.

## 검증 기록과 한계

- [BlueprintGeneratorTests.cs](../Assets/Tests/Editor/BlueprintGeneratorTests.cs), [PerlinLevelSamplerTests.cs](../Assets/Tests/Editor/PerlinLevelSamplerTests.cs), [TerrainLevelQuantizerTests.cs](../Assets/Tests/Editor/TerrainLevelQuantizerTests.cs)에 지형 데이터, 생성기, 양자화와 샘플러의 Editor 테스트가 있다.
- 같은 시드 재현 테스트는 새 샘플러와 생성기를 각각 만들어 두 청사진의 높이·종류를 비교한다. 검증용 고정 설정에서 물과 육지가 모두 있는지도 검사한다. 모든 시드에서 물과 육지가 공존한다는 보장은 아니다.
- 2026-10-08 `HasPath` 테스트 추가 전 연결된 Unity Editor에서 `run_tests --mode editor`로 57개 통과, 실패·스킵·미결정 0개를 확인했다. 이 중 RoadNetwork 테스트는 4개였다. 같은 좌표의 다른 높이 저장, 중복 ID 거부·기존 값 유지, 조회 실패 시 `out` 초기화, 직접 연결·비연결 및 두 번째 연결 후 기존 연결 보존을 검증했다.
- 이후 `HasPath`의 여러 구간 도달·고립 노드 테스트를 추가하고 전체 58개 중 57개 통과·1개 실패의 RED를 확인했다. 실패는 첫 `HasPath(17, 90)`에서 기대값 `true` 대신 뼈대의 `false`가 반환된 것이었다. 사용자 BFS 구현 후 현재 연결된 Editor에서 58개 모두 통과, 실패·스킵·미결정 0개의 GREEN을 확인했다. RoadNetwork 테스트는 5개다.
- BFS 방문 시점 비교를 위한 별도 메모리 진단에서, 갈라졌다 합쳐지는 도달 가능 노드 5개의 연결을 끝까지 탐색하는 루프에 횟수를 붙였다. 개선 전 꺼낼 때 방문 처리하는 순서는 큐에서 7회, 넣을 때 방문 처리하는 비교 순서는 5회 꺼냈다. 실행 시간 벤치마크는 아니다. 이후 사용자가 큐에 넣을 때 방문하도록 수정했고, 전체 Editor 테스트 58개 통과, 실패·스킵·미결정 0개를 다시 확인했다.
- 다음 자기 도달 테스트와 존재 검사 수정 후 전체 Editor 테스트 59개 통과, 실패·스킵·미결정 0개를 확인했다. 이어 사용자가 존재 검사를 탐색 진입 시 수행하도록 정리하고 한쪽 ID만 없는 조회를 같은 테스트에 추가했다. 그 시점 소스로 다시 실행한 결과도 59개 모두 통과, 실패·스킵·미결정 0개였다. RoadNetwork 테스트는 6개였다. 등록된 노드는 자기 간선 없이 자기 자신에 도달하며, 없는 동일 ID 및 한쪽 ID만 없는 조회는 `false`임을 검증했다. 이 새 테스트의 최초 RED는 AI가 실행 확인하지 않았으므로 RED를 직접 관찰했다고 기록하지 않는다.
- 이후 사용자가 수동 입체교차 테스트를 추가하고 역방향 조회까지 보강했다. 당시 연결된 Editor에서 다시 실행한 결과는 전체 60개 통과, 실패·스킵·미결정 0개였으며 RoadNetwork 테스트는 7개였다. 아래 도로 `17 ↔ 90`과 위 도로 `120 ↔ 180`은 양방향 도달 가능하고, 교차 중심 `42 ↔ 150`과 도로 간 끝점 `17 ↔ 180`은 양방향 도달 불가이며 `42 ↔ 150`의 직접 연결도 양방향으로 없다. 이 테스트는 기존 API를 조합한 회귀 사례이며 AI가 확인한 결과는 GREEN이다.
- 이어 램프용 중간 노드의 연결 테스트를 추가하고, 중심의 직접 비연결 및 기존 내부 경로 유지까지 보강했다. 당시 연결된 Editor에서 다시 실행한 결과는 전체 61개 통과, 실패·스킵·미결정 0개였으며 RoadNetwork 테스트는 8개였다. 연결 전과 `90 ↔ 200`만 연결한 뒤에는 `17 ↔ 180`의 양방향 도달이 없고, `200 ↔ 180`까지 연결한 뒤에는 양방향 도달이 생긴다. 교차 중심 `42 ↔ 150`의 양방향 도달도 확인했다. 연결 후에도 중심의 직접 연결은 양방향으로 없고, 기존 각 도로 내부 경로가 양방향으로 유지됨을 확인했다. 기존 API를 조합한 이 사례의 실제 확인 결과는 GREEN이다.
- 다음 터널 연결 테스트를 추가했다. 당시 연결된 Editor에서 실행한 결과는 전체 62개 통과, 실패·스킵·미결정 0개였으며 RoadNetwork 테스트는 9개였다. 내부 연결 전과 한쪽 연결 후에는 앞뒤 도로 사이에 도달하지 못하고, 양끝을 연결하면 양방향으로 도달한다. 입구·출구의 직접 비연결, 터널·지표 도로의 직접 및 경로 비연결, 기존 지표 내부 경로 유지도 양방향으로 검증한다. 이 사례는 기존 API를 조합한 그래프 계약이며, 실제 확인 결과는 GREEN이다.
- 지형과 물 위 도로의 분리 보관 테스트까지 추가한 그 시점 소스로 Editor 테스트 전체 63개 통과, 실패·스킵·미결정 0개를 확인했다. RoadNetwork 테스트는 10개다. 도로 연결 전후의 세 셀 바닥·종류·수면 유지, 물 위 도로의 독립적인 좌표·높이, 양방향 경유 경로와 끝점 직접 비연결을 검증했다. 이 결과의 범위는 분리 보관이며 교량 배치·형상·공간이나 차량 주행의 유효성은 아니다.
- 2026-10-09 포트 값 타입과 항상 `false`를 반환하는 판정 뼈대, 경계 높이의 두 테스트 사례를 추가한 그 시점 소스로 Editor 테스트 전체 65개 중 64개 통과·1개 실패, 스킵·미결정 0개를 확인했다. 기존 63개는 모두 통과했다. 같은 경계 높이의 양성 사례는 기대값 `true` 대신 `false`여서 실패했고, 다른 높이의 음성 사례는 통과했다. 의도한 첫 RED다.

## 바로 이어갈 작업

시작 전에 관련 이슈에서 이번 범위·제외 범위·검증 조건을 정한다. 아래 후보를 모두 한 이슈에 묶거나 순서대로 자동 진행하지 않는다. 없는 노드 연결의 상태 보존, 포트 소속 표현, 판정 후 연결 적용처럼 독립적으로 검증할 작업으로 나누고, 각 작업의 완료 조건과 필요한 검증·리뷰·문서 갱신을 마치면 다음 작업에 앞서 커밋을 추천한다. 큰 청사진 목표는 상위 이슈로 추적할 수 있으며, 하위 작업 완료와 상위 목표 완료를 구분한다. 실제 이슈 등록·변경과 커밋은 사용자 요청 범위를 따른다.

[#6](https://github.com/N0WST4NDUP/You-Said-Left/issues/6)의 없는 노드 연결 검증·리뷰·문서 갱신은 사용자 커밋 `ec7a6ce`에 포함되었다. [#7](https://github.com/N0WST4NDUP/You-Said-Left/issues/7)의 노드 ID별 포트 등록·조회와 상태 보존도 검증·리뷰했으므로 이번 범위의 커밋을 추천하고 다음 작업 지시를 기다린다. 사용자는 그 이후 노드와 도로 타일·모듈의 관계 및 `Coordinates`와 `CellCoordinates`의 중복 모델을 정리하기로 했다. 이번 저장 API로 한 노드가 한 타일이라는 대응을 확정하지 않는다. 관계 정리 이후 포트 판정을 통과한 경우에만 간선을 저장하는 별도 연결 단계를 검토한다. 실제 커밋·푸시·이슈 종료는 사용자 요청 범위를 따른다.

### #7: 노드 ID별 포트 등록·조회 검증 완료

사용자가 `AddPort(int ownerNodeId, RoadPort port)`, `IReadOnlyList<RoadPort> GetPorts(int ownerNodeId)`와 테스트 11개를 작성했다. ID별 목록에 여러 포트를 보관하며, 같은 값도 반복 저장한다. 노드·포트의 좌표와 높이 일치를 요구하지 않고 전달한 전체 값을 유지한다. 이는 보관 계약이며 물리적 배치·주행 유효성의 보장이 아니다.

등록과 조회는 없는 소속 ID면 상태 변경 전에 `ArgumentException`을 던진다. 등록된 노드의 빈 결과는 `Array.Empty<RoadPort>()`, 포트가 있는 결과는 `ToArray()`로 복사한 스냅샷이다. 추가 등록이 이전 결과를 바꾸지 않고 외부에서 반환 배열을 수정해도 내부 상태는 유지된다. 비어 있지 않은 조회는 호출마다 배열 복사를 수행하며, 캐시나 성능 측정은 이번 범위에 포함하지 않았다.

TDD 실행의 상세 기록은 [RoadNetwork API](api/road-network.md#실행-기록)에 있다. 첫 등록·조회의 전체 90개 중 89개 통과·1개 실패 → 사용자 구현 후 90개 GREEN, 스냅샷의 전체 92개 중 91개 통과·1개 실패 → 값 복사 구현 후 92개 GREEN은 AI가 실행 확인했다. 빈 결과 정식 테스트는 GREEN만 확인했고, 없는 노드 등록의 RED는 사용자 보고와 AI 실행 GREEN을 구분한다. 외부 수정 격리와 이후 보관·조회 경계 사례는 기존 구현의 회귀 GREEN이며 인위적인 RED는 만들지 않았다.

마지막 테스트는 서로 논리 경계가 맞는 포트를 노드 `17`, `42`에 차례로 등록한다. 각 단계에서 저장 성공을 확인하며 기존 `17 ↔ 90`의 직접 연결·경로 유지, `17 ↔ 42`와 `42 ↔ 90`의 직접 연결·경로 부재를 양방향 검사한다. 포트 등록과 간선 추가를 분리한 계약과 기존 Matcher 회귀를 함께 확인했다.

2026-10-10 최종 소스로 `unity command run_tests --mode editor --project-path "D:/01_Application/00_Personal/You Said Left" --format json --timeout 60`을 실행해 전체 100개 통과, 실패·스킵·미결정 0개를 확인했다. `dotnet run --project tools/RepositoryChecks --no-restore -- lint --all`은 C# 소스 9개 검사, 구문·규칙 위반 0개였다. 이번 범위의 커밋 대상은 `RoadNetwork.cs`, `RoadNetworkTests.cs`, `docs/api/road-network.md`, 이 문서다. #7의 독립 범위 완료와 상위 #5의 자동 생성 완료를 구분한다.

### Scene 미리보기의 별도 화면 검증

Scene 미리보기는 아직 화면 검증으로 남아 있다. 기본 디버그 설정은 소스 기준 `32 × 32`, `BaseLevel = 2`, `WaterLevel = 4`, `seed = 980306`이다. Scene에 저장된 Inspector 값은 다를 수 있으므로 직접 확인한다.

- Scene의 Gizmos와 컴포넌트 표시가 켜져 있는지 확인한다.
- Grass 윗면이 `cell.Level`에, Water 윗면이 공통 `WaterLevel`에 맞는지 확인한다.
- 물속 바닥은 셀마다 다른 높이를 가질 수 있고, 수면은 같은 높이에 놓이는지 확인한다.
- Inspector의 크기·시드·수면을 바꿨을 때 캐시를 비우고 다음 그리기에서 다시 생성하는지 확인한다.

### 수동 입체교차와 램프 검증

자동 도로 생성이나 동굴 생성 알고리즘부터 구현하지 않는다. `RoadNode`와 `RoadNetwork`의 노드 저장·조회 및 직접 연결 계약은 구현·검증했다. 다음 API는 테스트로 한 동작씩 정하고 사용자가 직접 구현한다.

`HasPath(int startNodeId, int destinationNodeId)`의 최소 BFS 구현, 큐에 넣을 때 방문하는 개선과 등록된 노드에 한정한 자기 도달은 GREEN을 확인했다. 출발·도착 ID를 탐색 전에 검사하고 반복문에서는 ID 비교만 하도록 정리했다. `HasPath(17, 999)`와 `HasPath(999, 17)`처럼 한쪽 ID만 없는 조회도 기존 자기 도달 테스트에 추가해 GREEN을 확인했다.

첫 사례는 **서로 다른 높이에서 평면상 교차하는 지상도로와 고가도로**다. 테스트용 연결은 양방향으로 명시한 고정 사례로 제한하고, 실제 도로의 일방통행 정책을 이 사례로 확정하지 않는다.

- 같은 수평 위치의 서로 다른 높이 도로가 함께 저장되어야 한다.
- 각 도로 내부에는 경로가 있어야 한다. 모든 연결을 끊어 비연결 검사만 통과하는 구현을 막는다.
- 두 도로 사이에는 경로가 없어야 한다. 좌표가 겹친다는 이유로 접속점을 합치지 않는다.
- 위 수동 입체교차의 경로 테스트를 작성하고 양방향 조회까지 보강해 GREEN을 확인했다. 이미 구현한 저장·연결·도달 API를 조합한 회귀 테스트다.

램프 사례는 별도 테스트에서 같은 두 도로를 구성한 뒤, 테스트용 중간 노드 `200`, 수평 좌표 `(3, 6)`, 높이 `2`를 추가했다. 이 노드는 이번 고정 사례의 램프 경유 지점을 나타낸다. 현재 API에는 램프 형식이나 물리적 유효성을 판단하는 계약이 없으므로 높이 `2`만으로 주행 가능성을 보장하지 않는다.

1. 연결 전에는 `17 ↔ 180`의 도달 여부가 양방향 `false`다.
2. `90 ↔ 200`만 추가한 뒤에도 두 도로 사이 도달 여부는 양방향 `false`다.
3. `200 ↔ 180`까지 추가하면 두 도로 사이 도달 여부가 양방향 `true`다.
4. 완성 후 `42 ↔ 150`은 직접 연결 없이 램프를 경유해 양방향 도달한다. 기존 두 도로 내부 경로도 양방향으로 유지되어야 한다.

위 램프 테스트를 작성·실행해 1~4의 GREEN을 확인했다. 완성 후 `HasDirectConnection(42, 150)`과 역방향의 `false`, `HasPath(17, 90)` 및 `HasPath(120, 180)`과 각각의 역방향 `true`도 검증한다. 전자는 교차 중심의 직접 연결이 추가되지 않았다는 계약, 후자는 기존 각 도로 내부 경로 보존을 검증한다. 이 사례의 검증 범위는 명시적 연결과 도달 관계이며, 램프 형상·포트·경사·공간과 실제 차량 주행은 후속 검증이다.

### 터널 입구·내부·출구 연결 검증

별도 테스트에서 아래 고정 사례를 구성했다. 입구·내부·출구는 이번 사례에서 노드에 부여한 역할이다. 현재 `RoadNode`에는 도로 종류나 터널 형상을 저장하는 필드가 없다.

| 역할 | ID | 수평 좌표 | 높이 |
|---|---|---|---|
| 입구 앞 도로 | 10 | `(0, 5)` | 1 |
| 터널 입구 | 17 | `(1, 5)` | 1 |
| 터널 내부 | 42 | `(2, 5)` | 1 |
| 터널 출구 | 90 | `(3, 5)` | 1 |
| 출구 뒤 도로 | 100 | `(4, 5)` | 1 |
| 지표 도로 시작 | 120 | `(2, 4)` | 3 |
| 지표 도로 중앙 | 150 | `(2, 5)` | 3 |
| 지표 도로 끝 | 180 | `(2, 6)` | 3 |

초기 연결은 `10 ↔ 17`, `90 ↔ 100`, `120 ↔ 150 ↔ 180`이다. 모든 조회는 양방향으로 검사한다.

1. 초기 상태에서 `HasPath(10, 100)`과 역방향은 `false`다.
2. `17 ↔ 42`만 추가한 뒤에도 입구 앞 도로에서 출구 뒤 도로로 도달하지 못한다.
3. `42 ↔ 90`까지 추가하면 `10 ↔ 100`의 도달 여부는 `true`다.
4. 완성 후 `17 ↔ 90`의 직접 연결은 없다. 입구와 출구는 내부 노드를 경유한다.
5. 터널 내부 `42`와 지표 도로 중앙 `150` 사이의 직접 연결과 경로는 모두 없다. 지표 도로 내부 `120 ↔ 180`의 경로는 유지된다.

이 테스트를 작성·실행해 모든 조회의 양방향 GREEN을 확인했다. 기존 저장·연결·조회 API를 조합한 회귀 사례다. 검증 범위는 터널 역할을 부여한 노드의 연결 계약이다. 지형 속 빈 공간과 덮는 지형, 차량 여유 공간, 모듈 포트와 실제 주행은 후속 검증이다.

### 지형과 물 위 도로의 분리 보관 검증

테스트용 생성기 `new BlueprintGenerator((x, y) => x == 1 ? 0 : 3)`로 `width = 3`, `height = 1`, `baseLevel = 0`, `waterLevel = 2`인 지형을 만든다. 바닥 높이는 `[3, 0, 3]`, 지형 종류는 `[Grass, Water, Grass]`이며 공통 수면은 `2`다. 생성 직후부터 이 기대값을 확인한다.

별도 `RoadNetwork`에 노드 `17 = (0, 0)`, `42 = (1, 0)`, `90 = (2, 0)`을 높이 `3`으로 저장하고 `17 ↔ 42 ↔ 90`을 명시적으로 연결한다. 도로 `42`는 같은 수평 위치의 물 셀 바닥 `0`, 수면 `2`와 별도 높이 `3`을 유지한다.

- 연결 후 `HasPath(17, 90)`과 역방향은 `true`, `HasDirectConnection(17, 90)`과 역방향은 `false`다.
- `TryGetNode(42, out ...)`의 성공과 도로 좌표 `(1, 0)`, 높이 `3`을 확인한다.
- 모든 지형 셀의 조회 성공, 바닥 `[3, 0, 3]`과 종류 `[Grass, Water, Grass]`, 공통 수면 `2`가 연결 후에도 유지되는지 확인한다.

이 테스트를 작성·실행해 GREEN을 확인했다. 현재 `RoadNetwork`와 `Blueprint`는 서로를 참조하지 않으므로 검증 범위는 두 데이터를 별도로 보관하는 고정 사례다. 물을 고려한 배치 검사, 교량 생성·형상·공간 유효성이나 실제 주행의 검증으로 해석하지 않는다.

### 현재 계약: 논리 격자 경계의 접속 후보

아래 값 타입과 경계 높이·반대 방향·이웃 셀 판정을 사용자가 작성했다. 실제 모듈의 포트 위치·폭을 추정하지 않고, 셀 주소와 바깥 방향으로 논리적인 경계를 지정한다. 현재 판정은 경계 높이의 동등 여부, X·Y축 반대 방향 쌍과 그 방향에 맞는 바로 이웃 셀을 검사한다.

- `RoadPortSide`: `PositiveX`, `NegativeX`, `PositiveY`, `NegativeY`. 수평 격자 좌표의 증가·감소 방향이며 월드의 동서남북과의 대응은 확정하지 않는다.
- `RoadPort`: 읽기 전용 값으로 `CellCoordinates`, `Side`, `BoundaryLevel`을 저장한다. 셀 주소는 실제 포트 접속점 좌표가 아니다.
- `BoundaryLevel`: 포트 끝점 주행면의 절대 경계 높이다. `RoadNode.Level`을 자동 복사하는 계약이 아니다. 경사 모듈은 양끝 경계 높이가 서로 다를 수 있다.
- `RoadPortMatcher.MatchesLogicalBoundary(first, second)`: 별도 정적 판정 메서드다. 두 경계 높이가 같고 방향이 반대이며 첫 방향에 맞는 바로 이웃 셀에 상대 포트가 있는 경우 `true`를 반환한다. 네트워크의 연결을 추가하거나 변경하지 않는다.

목표 조건은 상대 셀이 첫 포트가 바라보는 바로 다음 셀이고, 두 방향이 반대이며, 경계 높이가 같은 것이다. 첫 테스트에서는 인접성과 마주보는 방향을 입력으로 고정하고 높이만 바꾼다.

| 첫 포트 | 두 번째 포트 | 기대값 |
|---|---|---|
| `(2, 5)`, `PositiveX`, 경계 높이 `1` | `(3, 5)`, `NegativeX`, 경계 높이 `1` | `true` |
| 위와 동일 | 위와 동일하되 경계 높이 `2` | `false` |

인자 순서를 바꿔도 같은 결과여야 한다. [RoadPortTests.cs](../Assets/Tests/Editor/RoadPortTests.cs)에 위 두 사례와 각각의 역방향 조회를 작성했다. 뼈대 구현에서 양성 사례가 실패하는 RED를 확인했고, 사용자 높이 비교 구현 후 두 사례의 정방향·역방향 GREEN을 확인했다. 첫 GREEN만으로 방향과 위치의 불일치 검증까지 완료됐다고 보고하지 않는다.

작성한 방향 테스트는 두 셀 주소를 `(2, 5)`와 `(3, 5)`, 두 경계 높이를 `2`로 고정하고 첫 방향을 `PositiveX`로 둔다. 두 번째 방향이 `NegativeX`일 때만 `true`, `PositiveX`·`PositiveY`·`NegativeY`이면 `false`를 기대하고 각 인자 순서도 바꿔 검사한다. 처음 Editor 실행에서는 잘못된 방향의 세 사례가 실패했고, 사용자 방향 판정 구현 후에는 네 사례의 정방향·역방향 GREEN을 확인했다.

현재 구현은 높이가 같고 방향이 반대이며 셀 좌표가 그 방향의 한 칸 차이인 경우만 허용한다. 방향이 단순히 다르다는 비교는 직각 방향도 허용하므로 이 계약을 만족하지 않는다. enum 값의 숫자 순서에 의존하지 않고 방향 이름을 명시해서 비교한다. 두 축의 정상 접속과 잘못된 위치의 거부까지 GREEN을 확인했다.

작성한 Y축 회귀 테스트는 첫 포트를 `(2, 5)/PositiveY/경계 높이 2`, 두 번째 셀을 `(2, 6)`으로 고정한다. 두 번째 방향·높이가 `NegativeY/2`이면 `true`, `PositiveY/2`·`PositiveX/2`·`NegativeX/2`·`NegativeY/3`이면 `false`를 기대한다. 각 인자 순서도 바꿔 조회한다. `PositiveY`는 수평 격자 y의 증가 방향이며 수직 높이는 별도 `BoundaryLevel`이다. 실제 Editor 실행에서 다섯 사례의 정방향·역방향 GREEN을 확인했다. 이미 구현한 높이·방향 판정의 회귀 검증으로 진행했다.

작성한 X축 인접성 테스트는 첫 포트를 `(2, 5)/PositiveX/경계 높이 2`, 두 번째 방향·높이를 `NegativeX/2`로 고정하고 두 번째 셀 좌표만 바꾼다. `(3, 5)`이면 `true`, `(2, 5)`·`(4, 5)`·`(1, 5)`·`(2, 6)`·`(3, 6)`이면 `false`를 기대한다. 같은 셀, 두 칸 거리, 뒤쪽 이웃, 다른 축의 이웃과 대각선을 거부한다. 처음 Editor 실행에서 잘못된 위치의 다섯 사례가 실패하는 RED를 확인했고, 사용자 좌표 판정 구현 후 여섯 사례의 정방향·역방향 GREEN을 확인했다.

현재 구현은 높이 불일치의 조기 반환과 튜플 `switch`를 유지하고, 각 허용 방향 쌍에서 좌표를 비교한다. 두 번째 셀이 첫 번째 셀에 방향별 오프셋을 더한 좌표와 같아야 한다. 첫 방향에 따른 오프셋은 `PositiveX = (1, 0)`, `NegativeX = (-1, 0)`, `PositiveY = (0, 1)`, `NegativeY = (0, -1)`이다. 두 축의 정상 접속과 역방향 조회도 유지했다. 단순한 거리 한 칸 검사는 방향이 가리키는 경계를 보장하지 않는다.

작성한 Y축 위치 회귀 테스트는 첫 포트를 `(2, 5)/PositiveY/경계 높이 2`, 두 번째 방향·높이를 `NegativeY/2`로 고정한다. 두 번째 셀이 `(2, 6)`이면 `true`, `(2, 5)`·`(2, 7)`·`(2, 4)`·`(3, 5)`·`(3, 6)`이면 `false`를 기대하고 각 인자 순서도 바꿔 조회한다. 같은 셀, 두 칸 거리, 뒤쪽 이웃, 다른 축의 이웃과 대각선을 거부하는 여섯 사례다. 실제 Editor 실행에서 모든 정방향·역방향 GREEN을 확인했다. 이미 구현된 좌표 판정의 회귀 검증으로 진행했다.

이 표현은 논리적인 격자 경계 슬롯이며 실제 포트의 위치·가로 정렬·폭·단면이나 모듈의 조립·주행 가능성을 보장하지 않는다. 실제 포트 정보와 형식은 사용자 설명·Editor 확인으로 확보한 뒤 별도로 검증한다. 기존 `RoadNetwork.ConnectBidirectional`은 명시적 그래프 저장 계약을 유지한다. 서로 다른 노드 높이를 잇는 내부 램프 구간과 맞닿는 모듈 포트의 경계 높이 일치는 서로 다른 조건이다.

첫 저장 계약과 연결 검사를 한 번에 구현해야 하는 것은 아니다. 아직 구현하지 않은 동작은 한 테스트씩 나누어 RED → 사용자 최소 구현 → GREEN → 필요한 리팩터링·리뷰로 진행한다. 이미 구현한 동작의 회귀 테스트를 RED로 만들기 위해 코드를 일부러 깨뜨리지 않는다. 첫 단계의 완료는 **입체 도로의 저장과 명시적 연결 판정**이며 랜덤 생성·모듈 조립·실제 주행 완료가 아니다. 현재 합의한 독립 범위의 완료 조건을 충족하면 [작업 흐름](development-workflow.md)에 따라 커밋을 추천하고 다음 작업 지시를 기다린다.

연결 입력 경계의 세 회귀 사례는 GREEN을 확인했다. 후속 후보는 사용자 지시에 따라 독립 범위로 좁힌다.

| 단계 | 확인할 한 가지 동작 |
|---|---|
| 연결 입력 경계 — 검증 완료 | 없는 노드를 연결하면 예외가 발생하고 기존 연결을 유지하며 잘못된 직접 연결은 저장되지 않음. 첫 번째·두 번째·양쪽 ID 부재의 세 회귀 사례 GREEN |
| 소속과 연결 적용 | 노드 ID별 포트 보관·조회는 #7에서 검증 완료. 노드·타일·모듈과 좌표 관계 정리 후 모듈 소속·논리 판정의 간선 적용을 별도 계약으로 정함. 도로 형식은 실제 모듈 정보를 확보해 별도 검사 |
| 터널과 점유 공간 | 빈 통로와 위쪽 고체 지형을 함께 표현하고 차량 여유 공간·구조물 공간 충돌을 검사함 |
| 예약과 생성 | 주행 가능한 필수 경로 공간을 예약하고 건물·도로·장식 배치 후에도 연결·공간 조건을 유지함 |
| 조립과 지도 | Play Mode·Game View에서 실제 주행하고 같은 청사진의 지도와 대조함 |

기존 같은 높이 Grass 경로 제안은 이 입체 도로 계약 안의 지상도로 사례로 사용할 수 있다. 물·높이 차이를 일괄 차단하는 규칙을 최종 도로 규칙으로 채택하지 않는다. BFS는 정해진 연결 관계를 탐색하는 알고리즘 후보일 뿐 절차적 도로 생성 전체가 아니며, 비용·경로 선택과 BFS/A* 채택은 자동 생성 단계에서 정한다.

완료한 연결 입력 회귀 테스트는 각각 유효한 `17 ↔ 42` 연결을 만든 뒤 `(17, 999)`, `(999, 17)`, `(998, 999)` 요청을 거부하는지 확인한다. 예외뿐 아니라 기존 직접 연결의 양방향 유지, 실패한 요청의 양방향 직접 연결 부재, 없는 노드가 추가되지 않음과 기존 두 노드의 전체 값 보존을 검사한다. `HasPath`는 없는 ID를 먼저 거부하므로 그것만 검사하면 잘못 저장된 간선을 놓칠 수 있다. 현재 구현은 두 ID를 확인한 뒤 저장하며, 세 사례와 기존 Editor 테스트의 회귀 GREEN을 확인했다. #7에서는 같은 셀의 여러 노드와 경사 끝점 높이를 고려해 ID별 포트 소속을 보관하고, 좌표·높이 일치만으로 소속을 추론하지 않는 계약을 검증했다.

## 작업 방식

사용자는 테스트와 게임 코드를 직접 작성한다. 테스트 작성 → RED 확인 → 최소 구현 → GREEN 확인 → 테스트 빈틈과 경계 사례 리뷰 순서로 진행한다. AI는 설계·개념 설명·디버깅·리뷰를 기본으로 하고, 명시적으로 요청받은 범위의 코드만 수정한다.

다음 세션에서는 먼저 최신 Git 상태와 소스를 확인한다. 이 문서의 기록을 현재 실행 결과로 간주하지 않는다. 커밋과 푸시는 각각 요청된 범위에서만 수행한다.
